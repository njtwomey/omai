## 3. Reparameterised sampling for gamma, beta and Dirichlet [S][R]

The question of section 8.4: yes, they exist. `Distribution.rsample` and `hasRsample` are in `dists/distribution.ts`;
`dists/_sampling.ts` implements **implicit reparameterisation** (Figurnov et al. 2018, comment at line 31 and
`implicitReparam` at line 129) for gamma-based draws; the dists differentiate the sample in the parameters by one implicit
Newton step (`dists/_numeric.ts`). Run on 2026-11-10 (a scalar `rsample(key(1))` differentiated with `grad` at parameter 2.5
[R], script in the scratchpad; the point is that the derivative is not zero and not an error):

| distribution                                                                                                   | `hasRsample` | d sample / d parameter at 2.5 |
| -------------------------------------------------------------------------------------------------------------- | ------------ | ----------------------------- |
| gamma (concentration), gamma (rate), chi2, inverse gamma                                                       | true         | 0.569, -0.083, 0.341, -0.898  |
| beta (first shape)                                                                                             | true         | 0.0745                        |
| Dirichlet (concentration vector `[2.5, 2, 3]`, weighted sum)                                                   | true         | `[-0.0214, 0.0351, -0.0056]`  |
| Student t, von Mises, Weibull, log-normal, Cauchy, Laplace, exponential, half normal, truncated normal, normal | true         | all nonzero or 1              |
| Poisson (and every discrete family)                                                                            | **false**    | -                             |

So pathwise gradients exist for the continuous families that matter for guides. What guides can use them: every guide in
`guides.ts` (`autoDelta`, `autoNormal`, `autoMultivariateNormal`, `autoLowRankMultivariateNormal`, `autoLaplace`,
`autoIafNormal`: six, not five) is a **Gaussian or flow in unconstrained space pushed through `bijectorForSupport`**, so
they use `rsample` of a normal and never need the implicit gradient. A **hand-written guide with gamma, beta or Dirichlet
sites** works already: `traceElbo` (`elbo.ts` line 145 `scoreTerms`) adds score-function terms only for guide sites whose
`fn.hasRsample` is false, so such sites get pathwise gradients and discrete ones get the baseline score function. What is
missing is not the gradient but guides that **choose** such families (a gamma guide for a positive site, a Dirichlet guide
for a simplex), which the structured-guide work (algorithms C3) should offer as an option. Also `relaxed.ts` has Gumbel-softmax
and straight-through for discrete sites.

## 6. Facts the first lanes depend on [S]

### 6.1 Exponential families, conjugacy: what exists

`dists/exponential-family.ts` exports `exponentialFamily(dist): ExponentialFamilyForm` and the interface:

```ts
interface ExponentialFamilyForm {
  family: string
  natural: readonly Value[] // eta parts, batch shape + the part's own event axes
  partRanks: readonly number[] // trailing event axes per part (0 scalar, 1 vector, 2 matrix)
  sufficientStatistics(x: TensorLike): readonly Value[]
  logPartition(eta?: readonly Value[]): Value // A(eta), differentiable
  logBaseMeasure(x: TensorLike): Value
  meanParameters(): readonly Value[] // E[T] = grad A, by autodiff
  fisherInformation(): Value // Hessian of A, [..., k, k]
  fromNatural(eta: readonly Value[]): Distribution // same family, other natural parameters
}
```

Families with a form (`switch (dist.name)`, `exponential-family.ts` lines 175 to 469): **normal, logNormal, halfNormal,
exponential, gamma (also chi2, Erlang), inverseGamma, inverseGaussian, beta, weibull (shape fixed), pareto (scale fixed),
laplace (loc fixed), bernoulli, binomial (n fixed), poisson, geometric, negativeBinomial (r fixed), categorical,
oneHotCategorical, multinomial, dirichlet, multivariateNormal, wishart, vonMises**. Not there: truncated normal, Student t,
Gaussian with a precision-gamma joint (normal-gamma), inverse Wishart (conjugacy table has it, the form does not), Cauchy.
**Consequences for message passing:** the message types Gaussian, Gamma, Beta, Dirichlet, Discrete, Bernoulli, Poisson and
Wishart all have forms with `fromNatural` and `meanParameters`, so `product` and `division` of messages are sums and
differences of `natural` (there is no helper for that; it is two lines). **There is no truncated-Gaussian form**, so the
`is-positive`, `greater-than`, `max`, `min` operators must carry their own moments (the closed forms are `logNdtr`, `ndtr` in
`numerics/special`; `truncatedNormal` exists as a distribution in `dists/continuous/normal.ts:188`).

Conjugate updates: only the data-based table `CONJUGATES` (`dists/conjugacy.ts`, 17 pairs, `conjugatePrior(likelihood,
parameter)`, `conjugatePosterior(prior, likelihood, parameter, data, fixed)`) and its use in `probprog/engines/conjugate.ts`
(`conjugateData`, `conjugatePosteriors`, `conjugatePredictive`) and `gibbs.ts`. These take **observations stacked on axis 0**,
not natural-parameter increments. There is no generic "posterior natural = prior natural + sum of sufficient statistics"
routine; `exponentialFamily` gives everything needed to write it once (test it against the 17 pairs). Gaussian: `pgm/gaussian-factor.ts`
(below). Discrete: `pgm/factor.ts` log-space tables.

### 6.3 The `Space` / `Algorithm` / trace contract a method implements, and how a worker runs it [S]

- `Algorithm<S, K>` (`trace/algorithm.ts:116`): `name`, `config: Json`, optional `schema` (`channels({...})`, the older way), `init(key)`, `step(state, ctx)`, optional `done(state, t) -> RunStatus | undefined`, `observe(state, t) -> Observation { metrics, tensors, messages, frame }`, `serialise`/`deserialise` (needed for checkpoints, `seek`, `fork`, resume), `snapshot` (for algorithms that mutate state in place). `StepContext` has `t`, `key` (**derived from the run key and `t`**, so any pause and resume reproduces the run), `run`, `log`, `wants`, `emit`, `taps`.
- `Method<S, C, K>` (`trace/session.ts:43`): `name`, `config: DictSpace` (**knobs with defaults, "never functions"**), `make(config, key) -> Algorithm`, `contract` (a `Contract` or a function of config and key), `defaults` subscription, `hooks` by name, `projections`. `defineMethod` validates paths and defaults. `session(method, { config, seed, key, logs, mode, steps, checkpointEvery, past, start })` gives a `Session` with `advance(budget)`, `stateAt(t)`, `fork`, `probe`, `run()`.
- Contract (`trace/contract.ts`): `defineContract({ 'path/name': scalar() | tensor({role, shape, ...}) | message() | frame() | derived({...}) | event() })`, path type `K` inferred. Typed `ctx.log`/`ctx.emit` follow. `mcmcContract` (`probprog/engines/nuts.ts:45`) is the only probprog one.
- **Budgets and clocks.** `runFor(algorithm, { steps?, ms?, clock? }, { maxSteps, from })` (`algorithm.ts:435`) runs slices that "continue exactly where the last stopped"; **the library never reads a clock**: a time budget uses an injected `clock`. `scripts/banned.ts` bans `Date.now`, `performance.now`, `new Date`, `process.hrtime` and timers in published source. The worker host `serveProducer` (`render/src/producer/serve.ts:96`) owns the clock (`options.clock`, default `performance.now()`, marked `// allow: pacing of slices, never on the tape`), slices of `sliceMs` 20 and posts tape deltas every `postMs` 40. **Implication for the budget and snapshot requirement (plan decision 3): a method cannot implement a wall-clock budget or a one-second snapshot itself.** It exposes (a) a step small enough that the driver can stop between steps, (b) an iteration budget as a knob, (c) a cheap `snapshot` of its current posterior state (an `observe` or probe) that the driver (`runFor` with a clock, or the producer's `postMs`) reads at its own cadence. A time budget is then the driver's `ms`. The plan was edited to say so.
- **Running by name in a worker.** The page sends `{ type: 'init', id, method: 'name', options: WireOptions, variants, checkpoints, lookahead }` (`producer/protocol.ts`); the worker does `registry.need(name)` on a `methodRegistry([...methods])` (`producer/registry.ts`, **no import-time registration**: an app lists the methods it offers) and `session(method, sessionOptionsOf(wire))`. `WireOptions` = `config` (JSON), `seed`, `steps`, `checkpointEvery`, `past`, `logs`; a ready-made `key`, a `start` state or a function in config **throw**. Events back: `ready`, `tape` (deltas), `idle`, `probed`, `error`. `packages/meta` does **not** run methods: `meta/worker` is an empty placeholder (its header says "planned"); `meta/modules` is only the lazy-import map for the docs (it lists `omai-engine/probprog`, `.../probprog/engines`, `.../pgm`, `.../sampling`; a new entry point such as `omai-engine/message-passing` must be added there).
- **A finding that changes WP0 (the spec as JSON configuration).** The plan says the spec crosses to a worker "as JSON configuration". But `Method.config` is a `DictSpace` and `SessionOptions.config` is checked with `contains(space, config)`; a `SpaceValue` is only `number | string | boolean | number[] | SpaceValue[] | {k: SpaceValue}` (no `null`, no free string space, no JSON-with-nulls) (`space/types.ts:139`). So **a `ModelSpec` cannot ride in `Method.config` today.** Three options, to be decided in WP0: (1) a model registry in the worker by name (as datasets are chosen by name in estimator configs) with only the numeric data as knobs; (2) add a JSON `constructables` field to `WireOptions` and to `Method.make` (a change to `trace` and `render/producer`, outside the probprog lanes, needing the main session); (3) make `defineModel` return a `Method` per spec, built in the worker from the spec JSON by a registered factory. Recommendation: (1) for the first slice (benchmark models are named anyway), (2) for user-built specs.

### 6.4 Pieces for a fine-grained, resumable MCMC step [S]
