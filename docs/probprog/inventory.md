## 3. The twelve engines (`probprog/engines/`)

The contract (`engine.ts`): `name`, `form`, `description`, `applies(analysis) -> { applies, cost, quality, reason }`,
`run(model, data, analysis, { key, tracer, policy, parent }) -> Posterior`. Quality ranks exact, mcmc, weighted,
approximate, likelihood-free.

## 5. Sampling kernels (`sampling/`) and diagnostics

Kernels with the BlackJAX `init`/`step` shape (`chains.ts`): random-walk, independence and adaptive Metropolis
(`metropolis.ts`), blocked Gibbs, Neal's slice and elliptical slice (`gibbs.ts`), MALA, ULA, SGLD and SVGD (`langevin.ts`),
HMC, NUTS with Stan windowed adaptation, Riemannian HMC (`hamiltonian/`), tempered SMC and AIS (`smc.ts`), importance
sampling with PSIS (`importance.ts`), rejection samplers, gradient estimators (score function, pathwise, straight-through,
Gumbel-softmax), variance reduction (control variates, antithetic, stratified, RQMC). Diagnostics: R-hat (split and
rank-normalised), bulk and tail ESS, MCSE, HDI, autocorrelation, E-BFMI, divergence reports (`diagnostics/`).

Missing from BlackJAX's list (`match-blackjax.json`, 37 absent): MCLMC and adjusted MCLMC, SGHMC, SGNHT, Barker, ensemble
samplers, nested sampling, Pathfinder (partial), persistent SMC, CHEES and MEADS adaptation, low-rank window adaptation,
Schrodinger-Follmer, dynamic and multinomial HMC variants. Also absent: parallel tempering, MixedHMC, HMC within Gibbs, particle
MCMC.

**The gap that matters most is that none of these kernels is reachable from a program** except NUTS/HMC and the
engine-specific Gibbs: `probprog` builds the unconstrained `LogDensity` (`potentialEnergy`) but only wires two kernels to it.

## 6. Traces, sessions, render and the browser

- `trace/algorithm.ts`: `Algorithm` (`init`, `step`, `done`, `observe`, schema), `runAlgorithm`, `iterate`, `runFor` (time-budgeted
  slices); `trace/session.ts`: `Method`, `Session` (drive, seek, fork, probe); `trace/contract.ts`: `defineContract` with typed log
  paths. The MCMC driver and the init search use contracts; SVI, Gibbs, SMC and EM use the older `channels()` schema.
- `exposition/`: records such as `posteriorGrid`, `sequences`, `structure-steps` (a graph whose attributes follow a run),
  `diagrams`; `learn/bases/iterative.ts` gives estimators `.method`/`.session` for free.
- `packages/render/src/producer/` (`stage.ts`, `protocol.ts`, `serve.ts`): sessions are made in a Web Worker **by method name
  with JSON configuration**; `react/useJob.ts`: staged jobs with progress and cancellation; `trace/messages.ts` and
  `views/structure-steps.ts`: message timelines and graphs coloured by step. This machinery would draw a message-passing
  run today.
- Browser safety: `sideEffects: false`, one entry per folder, and `scripts/import-safe.test.ts` imports every entry point in Node
  with the browser's globals trapped. Chains in a worker work only if what crosses the boundary is JSON: **a model closure
  cannot be posted to a worker, a model spec can.** This is a main argument for the spec layer.

### Two timings (Node 24, this machine, run niced; one run each: an order of magnitude, not a benchmark)

| model                                  | engine                        | time   |
| -------------------------------------- | ----------------------------- | ------ |
| eight schools, centred, 10 latent dims | NUTS, 2 chains x (300 + 300)  | 4.0 s  |
| same                                   | SVI, 1,000 steps, auto normal | 0.21 s |
| logistic regression, n = 500, d = 10   | NUTS, 1 chain x (200 + 200)   | 1.4 s  |
| same                                   | SVI, 500 steps                | 0.23 s |

About 3 to 3.5 ms per NUTS iteration at these sizes, which is acceptable for a page (a browser is typically 1.5 to 3 times
slower than Node on this kind of numeric loop; not measured here). Every log-density evaluation re-runs the user's closure
through the handler stack and the autodiff transform, so per-evaluation cost is interpretive overhead plus tensor
allocation; it will matter above a few thousand observations per gradient. A compiled evaluation plan from a model spec
is the optimisation (plan section 5.7); measure first.

## 8. Why it feels primitive: specific causes

The brief says the system is "very primitive". The code is not primitive as a NumPyro port: the primitives, handlers,
densities, auto guides and twelve engines are broad and mostly tested against NumPyro. What a user meets is a different
set of problems, each grounded above:
1. **A model is a closure, not a value.** `Model<D> = (data: D) => unknown`. It cannot be inspected without running it, cannot be
   serialised, cannot cross a worker boundary, cannot be edited (`doIntervention` and `condition` wrap it), cannot be drawn
   except through a traced run, cannot be composed with a prefix, and is analysed from one run.
2. **Everything is by string name and raw tensor.** Sites are named by string and unique by convention; the user's
   arithmetic is tensor-function calls (`matmul(X, w)`, `mul`, `add`, `logistic`...) on untyped `Value`s; shapes are checked at
   run time; the posterior is read back by the same strings. There is no declared structure of dimensions: plates are
   dynamic scopes that allocate batch dimensions.
3. **Data binding is the closure's argument.** `D` is anything. Nothing declares which arrays are data, what their dimensions and
   supports are, what is missing, how a new batch or a new test set is bound for prediction.
4. **The user chooses an engine, not an inference.** `infer` picks one engine from a ranked list, or the user names one. There is no
   way to say "NUTS for these sites, an exact conditional for those, conjugate updates for the third", "EP for the likelihood
   but sample the hyperparameters", or "use my own proposal for the discrete part". `gibbs` decides by itself; nothing is
   configurable per site.
5. **Engines are not interchangeable pieces.** Engine options are plain objects of different shapes; only MCMC (and the init search)
   have a `Space` and a typed contract. SVI, Gibbs, SMC, EM and Laplace cannot be driven as sessions with automatic
   controls, compared in lockstep, or tuned, which every estimator in `learn` can.
6. **Whole-program applicability.** Conjugate, Gaussian, chain and enumeration engines apply only when the whole program matches;
   a model with one non-conjugate site falls through to a generic sampler and loses the exactness of the rest. There is no partial
   (structural) use of structure: no collapse, no Rao-Blackwellisation, no blocks.
7. **No message passing on programs.** EP, VMP and BP exist for discrete tables and for Gaussian-latent models on `pgm` model types;
   a program with a Gamma precision, a Dirichlet, a probit or truncated factor cannot be given to them.
8. **Kernels are not reachable.** The ten kernels of `sampling/` do not run on programs (only NUTS and HMC do).
9. **Coarse tapes.** The MCMC driver is one step; the others log an ELBO or a count per step. A session cannot pause, show chains
   filling in, or cancel inside a run for NUTS.
10. **Proof is thin where it matters.** Golden fixtures cover the building blocks (densities, handlers, ELBOs at fixed draws);
    the stochastic engines are checked against a handful of closed forms. Nothing says whether an engine's posterior is
    calibrated.
11. **Nothing shows it.** One example, no proof of concept, no diagnostic charts (the completeness survey's gap number 1), no
    factor-graph view of a program with its inference.
