# The failure convention and the status vocabulary of the numeric routines

Written 2026-11-07 for P3.20 (the convention part) and the remaining certain items of P3.30, under decision D-015 (failure
convention (a): numeric routines return a result with one `status` vocabulary and never throw for non-convergence; invalid
arguments throw `OmaiError('value')`; NaN rule (a): elementwise operations propagate, everything that summarises or decides
rejects non-finite input at its boundary). Sources: register rows ND-10, ND-11, OL-5, OL-7, OL-16, DSM-4, KDES-17, FD-16 and
the evidence in `numerics.md` F10 and F11, `optim-losses.md` F5, F7 and F16, `dists-stats-metrics.md` F4; every claim below was
re-checked against the code on main at `4ef92911`. The convention itself is in `docs/structure.md` section 2 ("Failure and
status") and in the summary of `lib/trace/events.ts`, which owns `RunStatus`.

## 2. The mapping

One `RunStatus`, no superset. Every word has a home; the table is `runStatusOf` in `trace/events.ts` and section 2 of
`docs/structure.md`:

| `RunStatus` | meaning                                                                                                     | older words                                                                                                         |
| ----------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `converged` | the convergence test was met, the optimum found                                                             | `optimal`, `converged`                                                                                              |
| `completed` | the budget (iterations, sweeps, evaluations, nodes) ran out with no verdict; an integration reached its end | `iteration limit`, `node limit`, `maximum iterations`, ODE and PDE `success`, BVP 1                                 |
| `stopped`   | the algorithm ended itself early by a rule: a stall, an event, an early exit                                | ODE `event`, matching pursuit with a dependent atom                                                                 |
| `diverged`  | the iterates left the finite numbers                                                                        | `NaN encountered`                                                                                                   |
| `failed`    | no answer exists or the method cannot continue                                                              | `infeasible`, `unbounded`, `numerical difficulties`, `derivative was zero`, `sign error`, ODE `failed`, BVP 2 and 3 |

Two judgement calls. (1) `infeasible` and `unbounded` are `failed`: the solver did its job and the answer is "there is none",
but the `RunStatus` has no verdict member, and the finer word stays in `status` for a caller who needs it. (2) A cap on the
algorithm's own iterations is `completed`, as the minimisers always had it (`out.status === 'completed'` means "maximum
number of iterations reached" in `optim/minimize/_shared.ts`); `stopped` is for a rule that ends the run early.

### The convention

1. A routine that returns a result record has `status: RunStatus` and `converged: boolean` (`converged === (status ===
   'converged')`), and does not throw because it did not converge.
2. Invalid arguments throw `OmaiError('value')`: a shape is `shape`; a NaN or an infinity where a number is needed, crossed
   bounds, a negative weight are `value`.
3. A routine that returns a bare value (a matrix function, a fitted polynomial, a differentiable solve) has no place for a
   status: it throws `OmaiError('convergence')` and its `@throws` says so. This is the one reading of D-015 that I had to
   interpret: D-015 says "never throw for non-convergence", but making these return a record would change their return types,
   a break of the public surface. The 12 + 7 sites are listed in section 5.
4. A result whose `status` field already holds an older vocabulary keeps it (additions only). The `RunStatus` is then beside
   it: `runStatus` in the four programming results (`status` and `success` stay; `converged` is added), `status` beside
   `flag` in `RootResult`. The ODE, PDE and BVP results keep their codes and gain nothing yet.

## 5. Left, with reasons (follow-ups)

- **Bare-value wrappers that throw `convergence`** (`sqrtm`, `signm`, `solveCare`, `solveDare`, `chebfun`, `continuedFraction`,
  `eigsh`, `schur`, kernels `eigh`/`svd`, `sparseSolve`, `emd`, `auction`, `bracket`, `curveFit`, `remez` in `approximation`, 19
  sites in `numerics` and `optim`): kept by convention rule 3. Where failure is an expected outcome the result-returning
  sibling should be used (`cg` for `sparseSolve`; `remezAlgorithm` and `chebfunAlgorithm` for the two approximations).
  `eigsh`, `chebfun`, `solveDare` and `solveCare` end their algorithm `failed` on the tape at the budget, pinned by tests;
  align them to `completed` when their result-returning variant exists.
- **Singular and non-finite input inside iterations**: `fsolve` and `broyden` throw `value` from `solve` for a singular Jacobian
  where the convention asks for `status: 'failed'`; `eigh`, `svd`, `cholesky` of a NaN matrix throw or return NaN
  (ND-11). They are kernels with many callers (`cholesky` feeds `choleskyJitter`'s retry) and need their own pass.
- **ODE, PDE, BVP, line searches and pattern search** keep `status`/`success` of their own; line searches are OL-11 (P3.28, the
  regex on messages), which the other agent's cluster work touches.
- **Results with `converged` and no `status` outside numerics and optim** (about 55: `linear`, `gam`, `gp`, `pgm`,
  `foundations`, `dynamics`, `information`, `kernel-methods`, `logic`, `graph`, `learn`): the same one-line addition, one
  domain at a time; no caller changes.
- **The tests (DSM-4)**: `TestResult` still has no `status`. P3.30 made the NaN rule hold (a NaN statistic is a NaN p), which
  is what the finding's own fix asks for; an optional `undefined` reason field is a design question left open (it changes the
  `TestResult` base type used by 60 tests).
- **Empty parameter vector (OL-16)**: bfgs, lbfgs and newton return `converged` in 0 steps; `nelderMead`, `powell`, `cmaes`
  throw `value 'no parameters'`. Under D-015 either is defensible (an empty problem is trivially solved, or an invalid
  argument); the finding recommends `converged`. Not changed: which one is a design question and the throwing ones have
  tests that pin the message.
- **Options validation** (`tol`, `maxIterations` finite and positive in the programming solvers): only the data was done;
  `linprogSimplex(..., { tol: NaN })` still answers.
- **KDES-17 error codes** (`domain` against `value`, inner messages): the rule is now stated (`structure.md`: `value` for
  arguments, `shape` for dimensions); the sweep of the 19 `domain` sites in kernels, data and exposition is mechanical and
  not part of the numeric routines.
- **FD-16** (`not-differentiable` used for "needs a concrete value" and "no rule"): a new `ErrorCode` member and about a dozen
  sites outside the numeric routines; left.
- **`OdeSolution` and `BvpSolution` status words**: mapped in the table, no field added (`status` is taken). Adding
  `runStatus` is the same one-liner as the programming results; left to avoid widening the surface in `dynamics` in this pass.
