## What I want

A TypeScript library, mdml-js, that re-creates the scope of the reference with a cleaner, more procedural structure. It is not a line-by-line port. It is a library, not a product. It publishes three packages (`mdml-engine`, `mdml-render`, `mdml-meta`) and contains two private apps: `apps/docs` (how to use the engine) and `apps/gallery` (what the renderer can draw). Other projects consume the packages, among them an encyclopedia and a tool that makes slide decks and blog posts. Everything here must serve those consumers: run, inspect, trace and draw every capability, and describe itself as structured data that they can render.

The scope is the union of the reference and this list: numerics, autodiff, distributions, statistics (including GAMs), classical ML (kernels and kernel expansion, SVM, trees, ensembles, Gaussian processes), neural networks (functional and torch-like Module/Sequential forms, and named architectures such as transformers), optimization, dynamics and sequential models, probabilistic programming, probabilistic graphical models (directed, undirected, factor graphs, with inference), logic and ILP, reinforcement learning with a gymnasium-like environment interface that makes new environments easy to add, and datasets. Areas that exist in the reference but not in this list (graph algorithms, signal processing, text, generative models, retrieval, evaluation, learning theory, information theory, vision and others) are in scope. Nothing is dropped except defects and duplicates.

The most important output of the first pass is the structure and strategy, not the amount of code: a clear, written definition of how the library is organised, how every reference module gets ported, and how the project continues to grow, written so that later sessions can carry the work forward from the repository alone (`port`, `audit`, `CLAUDE.md`) without this conversation.

## Deliverables

1. **The library repository.** Packages split by domain (for example `lib/{numerics|autodiff|dists|probprog|pgm|...}`), with the core libraries kept separate from applications of them. The compute side and the render side are separate packages. The render side is headless (it produces ECharts options, layouts and scene graphs), and the React bindings are kept in a separate package. It must be able to define and draw a graphical model and run inference on it, draw architecture diagrams (a transformer first), draw computation graphs, and wrap ECharts with a light and dark tab10 theme. Theme tokens are exported so that consumers can match them.
2. **The self-documenting layer.** Packages in which every capability of the compute and render sides is defined as typed, structured metadata (what it is, parameters, returns, concept links, references, runnable examples), published so that consumers can build pages from it. The exact split into packages is for you to decide after reading the reference.
3. **A parser and runner.** The parser reads all of the code and produces that metadata from docstrings and types. The runner executes every example in Node for tests and in the browser for consumers. It ships as a library API, plus a React binding that shows live output beside the code. The build fails when an example's stated output differs from its real output. Examples use a `// => value` convention for expected output, with `// => figure` or `// => trace` for visual results.
4. **Datasets.** These are part of the library and ship in the tarballs, so that every example works for everybody. Some are generated by seeded generators and some are static, vendored by uv scripts that record source, licence and checksum. Every dataset of the same task type has the same shape and loader interface. Regression, classification, ranking (recsys and IR), text corpora, time series, graphs, images and RL trajectories each have one schema and look the same, whether generated or static. Large datasets are GitHub release assets, downloaded on demand through the same loader, checked against a checksum and cached.

## Requirements

- **Tracked and traced.** Every iterative algorithm (training, optimization, sampling, inference, solvers, agents) emits typed trace events: runs, steps, metrics, parameters, seeds, messages, episodes. A run can be exported, replayed and visualised, and it records enough (seed, version, configuration) to reproduce it.
- **Procedural core.** Plain functions over explicit data, explicit seeded randomness, no hidden global state, no inheritance beyond one level. Class-style APIs are thin wrappers over the functional core, and both forms are documented.
- **Typed.** Strict TypeScript with no `any`. Dtype and shape in tensor types where this can be done cheaply, with clear runtime shape errors. Any data format that crosses a boundary (traces, metadata, datasets, the port map) has a schema and an inferred type.
- **Self-documenting.** Every export has a summary, parameter docs, a return description and at least one executable example.
- **Tested.** Unit tests with coverage thresholds, property-based tests (gradients against finite differences, distribution identities, decomposition reconstruction), golden fixtures from a Python oracle (uv, pydantic, numpy, scipy, scikit-learn, torch) so that tests need no Python at run time, doc-example tests, type tests, and browser tests for rendering and the example runner, run against a minimal harness page rather than an app. No `Math.random` outside the seeded RNG.
- **Consumable.** A smoke test installs the built tarballs into a throwaway Vite React project, imports every package entry point, runs an example and renders a figure there.
- **Built for expansion.** A new algorithm, layer, distribution, environment, dataset or graphical-model type is added by adding a module, not by editing existing ones. Tensor operations go through a backend interface so that WASM or WebGPU backends can be added later.
- **No reinvention.** Research existing libraries first and record decisions in `docs/decisions.md`. Core algorithms are implemented here so they can be traced and explained. External libraries are used for charting, graph layout, and as test oracles.

## Conventions

- Makefile at the top level as the single interface (`setup`, `dev`, `build`, `lint`, `format`, `typecheck`, `test`, `check`, `datasets`, `fixtures`, `pack`, `smoke` and whatever else the above needs).
- `mise` for tool versions, uv for anything Python, pnpm workspaces and Vite library mode for the web, a shared root `.env`, 120 columns everywhere, pydantic-settings CLI for Python scripts.
- A `CLAUDE.md` that tells Claude to use the make targets for all routine work.
- GitHub Actions for CI, and changesets for versioning. Release attaches the package tarballs and the large dataset assets to a GitHub release. There is no npm registry. All packages share one version, and consumers depend on the tarball URLs.
- Packages are ESM with proper `exports` and type declarations. The compute packages run in Node, the browser and a Web Worker without a bundler. React is a peer dependency of the bindings only.
